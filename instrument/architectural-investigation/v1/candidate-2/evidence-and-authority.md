# Evidence and Authority Semantics

## Evidence admissibility

An evidence item is admissible for a bounded claim only when it has an evidence
ID, exact source locator, immutable revision or an explicit unbound status,
declared evidence class, independently declared source-authority class, direct
versus inferential status, scope relationship, supporting capability,
limitations, and any contrary evidence. Inference is admissible only when every
premise is itself ledger-bound and the inference steps are recorded.

Admissibility means the item may be considered. It does not establish truth,
authority, sufficient support, maturity, execution, or promotion.

## Evidence-class contract

| Evidence class | May support | Cannot alone support | Directness | Revision binding | Execution implication | Conflict handling |
| --- | --- | --- | --- | --- | --- | --- |
| `NORMATIVE_SPECIFICATION` | Declared meaning, requirements, decision rules | Implementation, selection, execution, scientific correctness | Direct for declared text | Required | None | Conflict with another normative source is `CONTESTED` until explicit ownership/supersession is resolved |
| `NORMATIVE_BOUNDARY_DECLARATION` | Ownership, exclusions, authority boundaries | Behavior or scientific validity | Direct for declaration | Required | None | Preserve narrower and conflicting boundaries; no authority is imputed |
| `PROCEDURAL_DOCUMENTATION` | Declared process or invocation | Process use, result, success | Direct for procedure | Required for current claim | None | Compare with actual implementation/execution without treating either as universal authority |
| `DESCRIPTIVE_DOCUMENTATION` | Repository description and stated intent | Normative obligation, implementation, execution | Direct for wording; inferential for behavior | Required for current claim | None | Cannot override normative or direct execution evidence within their claim scope |
| `IMPLEMENTATION_SOURCE` | Static implementation structure and possible behavior | Selection, invocation, observed result, scientific correctness | Direct for source bytes; inferential for runtime | Required | None | Contrary runtime evidence contests the runtime claim, not source presence |
| `MACHINE_VALIDATABLE_CONTRACT` | Parseable structural constraints when validator semantics are bound | Semantic correctness, execution, authority | Direct for contract bytes | Required | None | Validator/contract disagreement is preserved and scoped to validated fields |
| `TEST_OR_FIXTURE` | Test/fixture presence and represented example | Discovery, CI selection, execution, pass, generality | Direct for bytes | Required | None | Contrary examples remain visible; fixture is not represented reality |
| `WORKFLOW_CONFIGURATION` | Declared selection and invocation path | Actual run or result | Direct for configuration | Required | None | Workflow history governs observed runs; configuration governs declared selection only |
| `EXECUTION_RECORD` | A bounded invocation/result when environment, command, revision, and output are bound | General correctness, repetition, transfer | Direct for preserved record | Required | Only the recorded execution | Conflicting records remain separate; do not average or discard failures |
| `GENERATED_ARTIFACT` | Generated bytes and declared projection | Source authority, reproducibility, currentness | Direct for generated bytes | Required | None unless generation record is separate | Source/projection conflict is visible; canonical status follows declared ownership, not generation |
| `REPOSITORY_METADATA` | Commit, tree, path, issue, branch, tag, or status facts | Normative readiness or semantic authority | Direct for observed metadata | Required for immutable claims | None | Branch/issue status cannot override content-bound records |
| `HISTORICAL_RECORD` | What a prior bounded record determined | Current state or current authority | Direct for history | Required | Only its recorded historical execution | Never rewritten by later evidence; later records may supersede prospectively |
| `EXTERNAL_PINNED_EVIDENCE` | External content at an immutable identity | Local ownership, current external state, transfer by itself | Direct for snapshot; interpretation may be inferential | Required | Only if execution record is also bound | External owner semantics remain external; local interpretation cannot replace them |
| `DIRECT_OBSERVATION` | What the operator directly observed within scope | Unobserved states or general behavior | Direct | Required when repository-relative; timestamp required otherwise | Only if the observation is an execution observation | Conflicting observations remain separate and trigger review |
| `INFERENCE` | A bounded conclusion from cited premises | New facts, authority, execution, missing premises | Inferential | All premises required | None | Contrary direct evidence contests the inference; premises and steps remain visible |
| `ABSENCE_OR_MISSING_EVIDENCE` | A bounded search failure or missing required support | Nonexistence outside the search boundary | Direct for search/result; inferential for absence claim | Search revision and rule required | None | Caps maturity at highest state not requiring the missing evidence |
| `CONTRADICTORY_EVIDENCE` | Existence and scope of disagreement | Resolution or preferred truth by itself | Direct or inferential as source dictates | Required | None | Claim becomes `CONTESTED`; no silent precedence or promotion eligibility |

## Source-authority contract

The canonical vocabulary has eleven values. Candidate.2 resolves the #78 prose
count discrepancy in favor of the eleven values actually enumerated; it does not
invent a twelfth class.

| Authority class | Authority scope | Cannot authorize |
| --- | --- | --- |
| `DECLARED_CANONICAL` | Producer-declared normative meaning for the bound revision and scope | Runtime facts, external acceptance, scientific truth |
| `NORMATIVE_SUPPORTING` | Normative detail subordinate to an identified canonical source | Override of canonical source without supersession |
| `IMPLEMENTATION_AUTHORITATIVE` | Source of implementation structure for the bound revision | Scientific meaning, workflow selection, execution result |
| `WORKFLOW_AUTHORITATIVE` | Required workflow selection/invocation semantics | Proof the workflow ran or passed |
| `REPOSITORY_STATUS_AUTHORITATIVE` | Git and repository status facts | Instrument readiness, audit authorization, semantic correctness |
| `HISTORICAL_ONLY` | Prior state and prior determinations | Current state or retroactive revision |
| `DESCRIPTIVE_ONLY` | Description, intent, orientation | Normative or executable claims |
| `EXTERNAL_RESOLVED` | Bound external producer evidence within its declared scope | Transfer of external authority to this repository |
| `EXTERNAL_UNRESOLVED` | Existence of an unresolved external dependency | Any positive capability or conformance claim |
| `NONAUTHORITATIVE_EXAMPLE` | Illustration or fixture representation | Normative meaning or generality |
| `UNKNOWN` | No authority claim | Any imputed capability, maturity, precedence, or promotion |

Authority is claim-relative, not a universal ranking. A single source can have
different authority classes for different claims, and the ledger must say why.

## Evidence-to-output boundary

```text
Evidence item
-> analyst interpretation with recorded judgment
-> validated bounded claim
-> boundary-decomposed finding
-> optional candidate recommendation
-> external owning authority decision
```

- Evidence does not become a conclusion without a ledger-bound interpretation.
- Structural validation can establish record integrity, not scientific validity.
- A validated finding is still bounded by scope, revision, limitations, and
  contrary evidence.
- A candidate abstraction is a proposal, not authority or promotion.
- Issue closure, artifact existence, model output, validation success, public
  visibility, and repository ownership do not create authority.

## Instrument authority boundary

The instrument may determine structural conformance of its record, execution
validity under its own procedure, bounded audit outcome, and evidence-supported
claim status. It cannot determine external governance acceptance, mutate
methodology or Structology, authorize another repository's mutation, establish
scientific truth, or grant audit authorization.
